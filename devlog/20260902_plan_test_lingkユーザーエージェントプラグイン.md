# test_lingk マルチLLM対応ユーザーエージェント：ひな形実装計画

作成日: 2026-09-02  
改定日: 2026-09-02

## 1. 目的

`lingk-user-agent` を、Codex、Claude Code、およびAgent Skillsを扱える他のLLMエージェントから利用できる、`test_lingk` 用の再利用可能なエージェント能力として構成する。

今回の到達点は「ひな形」までとする。利用者が自然言語で依頼したときに、対応するエージェントが `test_lingk` の前提、入力、ビルド、実行、出力確認の標準手順を選び、安全に案内・実行できる最小構造を計画する。計算・解析ロジックの作り込み、HPC投入、MCPサーバ、各marketplaceへの公開は次段階とする。

## 2. 議論から採用する設計原則

Notionのプロジェクトハブと、その配下の次の議論を参照した。

- [研究：エージェント連携開発ワークフロー](https://app.notion.com/p/9129cae3ff2183208f8c81a47d1e7b94)
- [AIエージェント協働を前提としたコード提供：スキル/CLI設計/プラグイン公開の考え方](https://app.notion.com/p/37d9cae3ff2181688237da64b936c055)
- [インストール可能なAIエージェント能力：Skills / Plugins / MCPの進展と研究用途](https://app.notion.com/p/3ce9cae3ff218148ab53fd224c1e3a66)

採用する原則は以下である。

1. 独自LLMやagent loopを作らず、汎用LLMエージェントへ研究固有の能力を追加する。
2. ベンダー中立な `SKILL.md`、参照資料、決定論的CLI／スクリプトを正本とする。
3. CodexやClaude Codeのmanifest、設定、導入手順は正本を包む薄いアダプターとし、専門知識を重複させない。
4. Skillは「いつ、何を、どの順序で使い、結果をどう読むか」を記述する。実処理はAIなしでも実行できる `test_lingk` 側のMakefile、実行ファイル、可視化スクリプト、将来のCLIへ置く。
5. 外部接続が必要になった場合も、可能なら共通MCPサーバを一つ実装し、対応クライアントから再利用する。
6. 特定製品だけが理解する機能は任意の追加要素とし、それがなくても基本利用フローが成立するようにする。
7. 認証情報、SSH設定、個人固有のパスはリポジトリへ含めない。

## 3. 対応範囲

初期対応対象は、Codex、Claude Code、`SKILL.md` を読み込めるその他のエージェント、および `AGENTS.md` または同等の指示ファイルを利用できるエージェントとする。

ここでいう「対応」は、同じSkill本文と参照資料を用いてローカルの `test_lingk` 利用フローを案内・実行できることを指す。各製品のUI、marketplace、独自hooks、独自サブエージェント機能を完全に揃えることは初期要件に含めない。

初期対象外は以下とする。

- 製品固有の自動化を前提にした処理
- HPC／SLURMへのジョブ投入と長時間実行の状態管理
- 物理的妥当性や収束の自動保証
- Codex、Claude Codeそれぞれのmarketplaceへの公開

## 4. 現状把握

### `lingk-user-agent`

- 現在は `README.md` と `LICENSE` のみで、共通Skill、エージェント指示、製品別manifestはない。
- 独立したGitリポジトリであり、ベンダー中立な正本と製品別アダプターをまとめる配置先として使える。

### `test_lingk`

- Fortran製の線形ジャイロ運動論方程式ソルバ。
- `make lingk` で `lingk.exe` をビルドする。現行MakefileはGNU Fortranを選択している。
- `param.namelist` から物理パラメータを読み、`data/` に結果を出力する。
- 主な出力は `frq.001`、`mominzt.001`、`fkinzv_imXXXX_tYYYYYYYY.dat`。
- gnuplotスクリプトで結果を確認できる。
- 一部の主要数値条件は `src/parameters.f90` のコンパイル時定数であり、変更時には再ビルドが必要。
- 現時点の標準実行フローを担う独立CLIやPythonテストは見当たらない。

最初のSkillは存在しないCLIを前提にせず、現在の公開インターフェースを扱う。将来CLIを導入した際もSkillの利用意図を維持できるよう、具体的な処理ロジックはSkillへ埋め込まない。

## 5. アーキテクチャ

構成を「共通コア」「リポジトリ文脈」「製品別アダプター」の3層に分ける。

```text
lingk-user-agent/
├── skills/                         # ベンダー中立な能力の正本
│   └── use-test-lingk/
│       ├── SKILL.md
│       └── references/
│           ├── parameters.md
│           └── outputs.md
├── AGENTS.md                       # ベンダー中立なリポジトリ作業規範
├── CLAUDE.md                       # Claude Code用の薄い入口
├── .codex-plugin/                  # Codex用アダプター
│   └── plugin.json
├── .claude-plugin/                 # Claude Code用アダプター候補
│   └── plugin.json
├── devlog/
├── README.md
└── LICENSE
```

製品別仕様は変化し得るため、`.claude-plugin/` を含む正確なmanifest名・配置・必須項目は、実装開始時に各製品の公式仕様で再確認する。不要または未対応のアダプターを推測した形式で置かない。

### 共通コア

- `skills/use-test-lingk/` の `SKILL.md` と参照資料を能力の正本とし、製品別に本文を複製しない。
- frontmatterはAgent Skillsで広く解釈できる最小項目を基本とする。
- 特定製品のツール名、権限モード、UI操作は共通Skillの必須手順へ混ぜない。
- 製品差が避けられない場合だけ、短いアダプター資料へ分離する。

### リポジトリ文脈

- `AGENTS.md` を、構成、正本の所在、検証方法、安全規則を記す共通文書とする。
- `CLAUDE.md` は `AGENTS.md` を参照する薄い入口とする。シンボリックリンクは配布・Windows互換性を確認してから選ぶ。
- 同じ規則を複数ファイルへコピーせず、更新時の不一致を防ぐ。
- 他クライアントが専用指示ファイルを要求する場合も同じ方針で追加する。

### 製品別アダプター

- Codexのmanifestには共通 `skills/` への参照と表示用メタデータだけを持たせる。
- Claude Codeのplugin manifest／配布設定にも同じ共通Skillを参照させる。
- marketplace、UI metadata、hooks、独自agentsは必要になった段階で追加する任意機能とする。
- アダプターの有無によってSkillの挙動や安全規則が変わらないようにする。

### 将来のツール接続

- CLIは人間、CI、すべての対応エージェントから同じように呼べる独立成果物とする。
- MCPが必要になった場合は標準プロトコルに沿った共通サーバとし、製品別manifestは接続設定だけを持つ。
- CLIやMCPが使えないエージェントでも、説明と手動実行手順までは利用できる段階的縮退を設計する。

## 6. 最初のSkillの責務

`skills/use-test-lingk/SKILL.md` は次のローカル利用フローに限定する。

1. `test_lingk` の場所と必要コマンド（GNU Fortran、make、必要に応じてgnuplot）を確認する。
2. 実行前に `param.namelist` とコンパイル時定数の違いを説明する。
3. 既存入力を保護し、変更内容を利用者へ明示する。
4. `data/` の既存結果を不用意に消さず、ビルドと実行を行う。
5. 終了コードと生成物を確認し、`frq.001` を中心に結果の所在を報告する。
6. 可視化を依頼された場合だけgnuplotを使う。GUIや長時間実行が必要なら事前に伝える。

descriptionは「lingkの設定、ビルド、ローカル実行、出力確認を依頼されたとき」に選択される具体性を持たせる。特定エージェント名はトリガー条件にせず、物理的妥当性の保証、収束判定の断定、HPC投入まで対応するような過大な表現も避ける。

`references/parameters.md` ではnamelistとコンパイル時パラメータを分離し、不明な単位や許容範囲を推測で補わない。`references/outputs.md` では出力形式、生成条件、対応するgnuplotスクリプトを整理し、バイナリ形式を固定的に一般化しすぎない。

## 7. 実装手順

### Phase 1: 共通仕様と安全境界の確定

- `test_lingk` のREADME、Makefile、namelist、ソース、出力処理、plotスクリプトを照合する。
- `lingk.exe` と `data/` の既存結果を考慮し、「既存成果物を削除しない」規則を入れる。
- `make clear` と `make clean` は破壊的操作を含むため、自動実行する標準フローから外す。
- 固定絶対パスを保存せずに `test_lingk` を解決する方針と、共通Skillが依存できる最小限の操作能力を定める。

### Phase 2: ベンダー中立コアの作成

- `skills/use-test-lingk/`、`SKILL.md`、必要なreference文書を作る。
- `AGENTS.md` に正本の所在、作業規範、検証、安全境界を記載する。
- READMEに対応エージェント、共通部分、製品別導入方法、非対応範囲を整理する。
- Skill本文からCodex固有語、Claude固有語、製品固有の権限設定を排除する。

### Phase 3: 製品別アダプターの作成

- 実装時点の公式ドキュメントで、CodexとClaude CodeのSkills／Plugin仕様を確認する。
- 両製品のmanifestまたは所定のplugin構造から、同じ共通 `skills/` を参照させる。
- `CLAUDE.md` は `AGENTS.md` を参照する最小内容または互換性を確認したリンクとする。
- その他のエージェント向けには、共通Skillを直接読み込む手動導入手順をREADMEへ記載する。
- 初期版では各marketplaceへの登録を行わない。

### Phase 4: 静的・互換性検証

- 共通Skillを汎用のSkill validatorで検証する。
- CodexとClaude Codeの各manifestを、それぞれの公式validatorまたはCLI検査機能で検証する。
- 各エージェントでSkillが検出され、同じ代表依頼に対して同じ安全境界と基本手順を選ぶことを確認する。
- 製品別ファイルに研究知識や実行ロジックが重複していないことを確認する。
- 未完了placeholder、存在しない参照、固定絶対パス、秘密情報がないことを確認する。

### Phase 5: 最小スモークテスト

- 既存の `test_lingk` を変更せず、コンパイラとmakeの存在確認を行う。
- 必要な場合だけ `make lingk` を実行し、ビルド成功を確認する。
- 既存 `data/` を保護した分離実行ができなければ、ひな形段階では実行を保留する。
- 実行する場合は終了コード、期待される3系統の出力、`frq.001` の非空性を確認する。
- 少なくともCodexとClaude Codeで同じスモークテスト手順を利用できることを確認する。

## 8. ひな形の完了条件

- `skills/use-test-lingk/` がベンダー中立な正本として一か所に存在する。
- Skillが適用条件、前提確認、入力、ビルド、実行、出力確認、安全上の注意を記述している。
- `AGENTS.md` と `CLAUDE.md` の関係が明確で、規則の重複管理がない。
- CodexとClaude Codeの両方で、公式仕様に沿ってSkillを検出または導入できる。
- 製品別manifestは薄いアダプターであり、共通Skillの内容を複製していない。
- Skill内に科学計算ロジックを複製していない。
- 実装していないMCP、Apps、hooksなどをmanifestが参照していない。
- READMEだけで共通機能、対応範囲、製品別導入方法、制限が分かる。
- 既存の `test_lingk` の入力、ソース、実行ファイル、結果を破壊していない。
- 検証結果と製品ごとの差異がdevlogへ記録されている。

## 9. ひな形後の拡張候補

1. `test_lingk` 側に、ケース作成、設定検証、実行、状態確認、出力要約を担う独立CLIを実装する。
2. 共通Skillの実行先をMakefile／直接実行からCLIへ置き換える。
3. 小さな基準ケースと期待値を用意し、回帰テストと物理的妥当性チェックを分ける。
4. 出力解析Skillを目的別に分割する。
5. 外部接続が必要になった時点で、複数エージェントから使える共通MCPを検討する。
6. 配布先が決まった後に、各marketplace用metadata、公開URL、導入・更新手順を追加する。
7. Gemini CLI、GitHub Copilot、Cursor等は、共通Skill形式への対応と公式仕様を確認してアダプターまたは導入手順を追加する。

## 10. 実装開始時の前提

- CodexとClaude Codeを初期の同格な検証対象とする。
- 能力の正本は `skills/use-test-lingk/` とし、製品別ディレクトリへ複製しない。
- リポジトリ名は当面 `lingk-user-agent` を維持する。製品別plugin IDは、各仕様で同じ名前が有効なら揃える。
- 最初の標準ケースは、現在の `param.namelist` と `ns = 1` を使うローカル実行とする。
- 著者名、公開repository URL、ホームページ、問い合わせ先は公開準備時に確定する。
- 物理的妥当性の判定基準は現行READMEだけでは不足しているため、初期版はファイル生成と形式確認までに限定する。

## 11. 推奨する最初の実装単位

次の作業ではPhase 1からPhase 4までを一つの変更として実施し、共通SkillとCodex／Claude Codeアダプターを同時にレビュー可能にする。実計算やHPC連携へ進む前に、両エージェントが同じ正本を読み、同じ安全境界で動作することを確認する。

なお、本改定では計画書のみを変更し、manifest、Skill、指示ファイルなどの実装は行わない。
